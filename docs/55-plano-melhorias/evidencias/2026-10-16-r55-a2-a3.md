## Atenção: a execução padrão importa 0 raw items
Como toda fonte nova chega desabilitada e só os raw items de fontes habilitadas **nesta execução** são migrados, uma execução sem `--enable-limit` importa 0 raw items (e 0 execuções sintéticas). O pipeline recoleta as vagas depois que o dono habilita as fontes. Os raw items de 7 dias só entram com `--enable-limit N` e só de fontes novas; hoje o banco local não tem nenhum dessa janela, então o resultado é 0 de qualquer forma.

## Como funciona (`scripts/migrate_catalog.py`)
- `export --from-container <nome>`: uma única sessão `psql` numa transação `REPEATABLE READ READ ONLY` (snapshot consistente), credenciais do ambiente do próprio container, stderr descartado, processo encerrado em `finally`. `SOURCE_DATABASE_URL` serve de alternativa.
- `import --export <arquivo> --owner-sub-file <arquivo> [--enable-limit N] [--apply]` em `DATABASE_URL`: exige o alvo no head do Alembic. Dry-run é o padrão: tudo numa transação com rollback, então as contagens são exatas e nada fica gravado.
- Só insere (`ON CONFLICT DO NOTHING`/`WHERE NOT EXISTS`); linhas já presentes no alvo nunca são alteradas, adotadas nem recebem filhos.
- Identidade da fonte = endpoint do provedor, não o nome: greenhouse `board_token`; ashby `board_identifier`; lever `site_identifier`+`api_region`; workable `account_identifier`; inhire `tenant_identifier`; workday `tenant_identifier`+`api_region`; teamtailor e factorial `company_identifier`; jobposting `page_url`; `api_region` do lever assume `global` quando ausente (como em `probing.py`); tipos sem chave (manual, remotive, hacker_news) por (tipo, nome). Chave ausente = identidade desconhecida (`sources_identity_unknown`): cai para o casamento por (tipo, nome) e nunca casa com outro nome nem gera conflito. Cada fonte local: mesmo (tipo, nome) e mesmo endpoint -> `sources_preexisting`, ignorada; mesmo (tipo, nome) e endpoint diferente -> `source_conflicts`, a fonte e tudo sob ela são ignorados; mesmo endpoint com outro nome -> `sources_matched_other_name`; senão é nova.
- Fonte, sonda e raw item de fonte já existente não entram; revisões só para `company_source` novos; evidência de startup só para empresas novas; conflito de domínio de empresa é contado (`company_domain_conflicts`).
- Diferença de schema 0068 para o head: importa só as colunas comuns às duas pontas (as linhas de uma tabela precisam ter o mesmo conjunto de chaves); colunas só do alvo (por exemplo `source_run.skipped_stale`) usam o default. JSON escalar é serializado conforme o tipo da coluna de destino.
- Habilitação: toda fonte nova chega **desabilitada** (padrão). `--enable-limit N` habilita até N fontes novas que estavam habilitadas e homologadas localmente (regra do painel: `evidence_status=confirmed`, `reviewed_at`, `terms_reviewed`, `collector_local_tested`; `manual` isenta), na ordem (prioridade, tipo, nome), para o dono ligar aos poucos. Homologação e sondas são preservadas de qualquer forma. Os contadores `sources_new_enabled/disabled` vêm das linhas realmente inseridas.
- Raw items: só de fontes novas habilitadas. Uma `source_run` sintética `SUCCEEDED` por fonte nova (id determinístico, `correlation_id=r55-catalog-migration`), com horários no `fetched_at` mais novo dos itens e contadores = linhas realmente inseridas. Nenhuma execução sintética para fonte pré-existente.
- `owner_sub`: nenhuma tabela do catálogo tem a coluna no head (a 0069 só cobre career_profile, application_process, saved_search, relevance_mark e match_assessment). O sub continua obrigatório e é gravado em qualquer tabela migrada que tenha a coluna. O engine usa `hide_parameters=True`; erros imprimem só a classe e o SQLSTATE (o DETAIL do Postgres pode citar a linha com o sub).
